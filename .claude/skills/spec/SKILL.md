# /spec — Structured spec before implementation

`AGENTS.md` gates Critical-tier changes behind an approved spec. `/spec <issue>`
reads the issue with `gh issue view`, picks a format, and posts the spec as an
issue comment for review.

**Do not write implementation until the spec is approved.** Tests may be
written from the spec — each row is a test case.

## Format selection

| Change shape | Format | Telltale signs |
|---|---|---|
| Alters or asserts a mathematical property | **Invariant table** | "should equal", "is independent of", "must hold for all" |
| Numerical method / integrator / solver | **EARS + error budget** | step sizes, tolerances, convergence, termination |
| Discrete/combinatorial logic | **Decision table** | tack × band × boundary combinations |
| Lifecycle or multi-state flow | **State diagram** (Mermaid) | named states, transitions |

If none add value, say so and skip — not every issue needs a spec.

## Invariant table — the default here

The most useful format for this codebase. Columns:

| Invariant | Statement | Holds when | **Negative control** | Tolerance |
|---|---|---|---|---|
| I1 | `L_path = L / cos θ` | always, any `N` | `θ → π/2` ⟹ `.infinity` | rel `1e-12` |
| I3 | unfolded polyline colinear | tacks alternate | constant tack ⟹ **not** colinear | abs `1e-9` |

Rules:
- **Every row is at least two test cases** — the positive and the negative
  control. A row without a negative control is not accepted (see `AGENTS.md`
  § "The falsifiability rule").
- Reference existing invariants by their `docs/invariants.md` ID (`I1`…`I8`)
  rather than restating them. New invariants get the next free ID and are added
  to that doc in the same PR.
- State the tolerance and *why* — bare epsilons get bounced in review.

## EARS + error budget — for numerical methods

| Pattern | Template |
|---|---|
| Ubiquitous | THE SYSTEM SHALL \<action\> |
| Event-driven | WHEN \<trigger\> THE SYSTEM SHALL \<action\> |
| State-driven | WHILE \<state\> THE SYSTEM SHALL \<action\> |
| Conditional | IF \<condition\> THEN THE SYSTEM SHALL \<action\> |

One requirement per line, each independently testable, each with a *measurable*
condition. For anything integrated, add an explicit error budget:

```
THE SYSTEM SHALL report a termination reason of `.arrived`, `.stalled`, or
  `.exceededStepBudget` for every integration.
WHEN the field is linear THE SYSTEM SHALL arrive within 1e-3 · L of B.
WHEN the step length is halved THE SYSTEM SHALL reduce arrival error by at
  least 40% (first-order convergence).
IF |∇s| < 1e-12 THEN THE SYSTEM SHALL terminate with `.stalled` rather than
  emitting a NaN step.
```

"Quickly", "accurately", "reliably" are not measurable — reject them in your
own draft.

## Decision table

Columns are every input that affects the outcome; one output column; every
meaningful combination present. Mark impossible rows `n/a` rather than omitting
them — an omitted row reads as an oversight.

## State diagram

Mermaid `stateDiagram-v2` so it renders on GitHub. Name every state and every
transition trigger; list guard conditions below the diagram.

## Posting

```bash
gh issue comment <number> --body "$(cat <<'EOF'
## Structured Spec

**Risk tier:** Critical
**Format:** Invariant table
**Invariants touched:** I3, I4  (docs/invariants.md)

<spec content>

### Test plan

| Spec row | Test | File |
|---|---|---|
| I3 positive | `alternatingUnfoldsStraight` | `UnfoldingTests.swift` |
| I3 negative | `constantTackDoesNotUnfoldStraight` | `UnfoldingTests.swift` |

---
*Generated by /spec. Review and approve before implementation begins.
Every row is at least two test cases: the property and its negative control.*
EOF
)"
```

After approval, save the spec to `docs/specs/<issue>-<slug>.md` in the
implementing PR so it survives outside the issue tracker.
